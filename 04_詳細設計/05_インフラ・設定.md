# 詳細設計書 05 インフラ・設定

版：1.0／作成日：2026年10月31日
関連：[基本設計書 3章](../03_基本設計書.md)、[00_実装ガイド](./00_実装ガイド.md)

本アプリは本番稼働させない。以下は「Azure上のテスト環境」と「開発者のPCのローカル環境」の2つを定める。

## 1. Azureの構成

| リソース | 名前（例。`<sfx>` は全体で一意にする任意の英小文字・数字） | 設定 |
|---|---|---|
| リソースグループ | `rg-pickup-app` | リージョン：Japan East |
| App Serviceプラン（Frontend） | `plan-pickup-front` | Linux、**Free（F1）** |
| App Serviceプラン（Backend） | `plan-pickup-back` | Linux、**Free（F1）** |
| Web App（Frontend） | `app-pickup-front-<sfx>` | ランタイム Node 24 LTS |
| Web App（Backend） | `app-pickup-back-<sfx>` | ランタイム Python 3.12 |
| PostgreSQL | `psql-pickup-<sfx>` | Azure Database for PostgreSQL Flexible Server、PostgreSQL 17、Burstable **B1ms**、ストレージ32GB、バックアップ保持7日、高可用性なし |
| データベース | `pickup` | 上のサーバー内に作成 |

- Free（F1）の主な制限：Always Onなし、CPU時間60分/日、メモリ1GB、インスタンス1つ（[Microsoft Learn：App Serviceの制限](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/azure-subscription-service-limits#azure-app-service-limits)）。通信がしばらくないとアプリが停止し、次のアクセスで起動する（数十秒かかることがある）。
- Free（F1）のLinuxプランを2つ作れない場合は、1つのF1プランに2つのWeb Appを載せる（CPU時間などの上限は2アプリで共有になる）。
- 試験中にCPU時間の上限でアプリが止まる場合は、プランを Basic（B1）に変更する。アプリ側の変更は不要。
- Key Vault と Application Insights は使わない。秘密情報は Web App の「環境変数（アプリ設定）」に置く（画面上は値を隠して保存される）。
- 使わない間は PostgreSQL を停止して費用を抑える（`az postgres flexible-server stop`）。Azureの仕様で停止したサーバーは7日後に自動で起動する。
- 料金はAzureの価格ページで確認する。Azure無料アカウントの場合、PostgreSQLのB1msは一定時間まで無料枠の対象になることがある。

### 1.1 PostgreSQLの接続設定

- 公開アクセス（パブリックアクセス）を有効にし、ファイアウォールで「Azure内のサービスからのアクセスを許可」と開発者のIPアドレスだけを許可する。
- SSL必須（`sslmode=require`）。
- 管理者ユーザーとは別に、アプリ用のユーザー `pickup_app` を作り、データベース `pickup` のスキーマ `public` の作成・読み書き権限だけを与える（マイグレーションも同じユーザーで行う）。

## 3. 起動とデプロイ

### 3.1 Backend

- `backend/requirements.txt` に00_実装ガイド 2.1の版を固定して書く。
- `backend/startup.sh`：`alembic upgrade head` を実行してから `gunicorn -k uvicorn.workers.UvicornWorker --bind=0.0.0.0:8000 --workers 1 --timeout 120 app.main:app` を起動する。
- Web Appの「スタートアップコマンド」に `bash startup.sh` を設定する。
- ヘルスチェック用に `GET /healthz`（認証なし、DBに `SELECT 1` して `{"status":"ok"}`）を用意する。BFFの秘密ヘッダー確認の対象外とする。

### 3.2 Frontend

- `next.config.ts` に `output: "standalone"` を設定する。
- GitHub Actionsで `npm ci` → `npm run build` → `.next/standalone` に `.next/static` と `public` をコピー → そのフォルダをZIPにしてデプロイする。
- Web Appのスタートアップコマンド：`node server.js`。アプリ設定 `SCM_DO_BUILD_DURING_DEPLOYMENT=false`。App Serviceが渡す `PORT` 環境変数でNext.jsが待ち受ける。
- `next.config.ts` の `headers()` で、全ページに次のレスポンスヘッダーを付ける（Stripeの決済画面と3Dセキュアを動かすための許可を含む）。

| ヘッダー | 値 |
|---|---|
| Content-Security-Policy | `default-src 'self'; script-src 'self' 'unsafe-inline' https://js.stripe.com https://*.js.stripe.com; style-src 'self' 'unsafe-inline'; img-src 'self' data: https://*.stripe.com; connect-src 'self' https://api.stripe.com; frame-src https://js.stripe.com https://*.js.stripe.com https://hooks.stripe.com; frame-ancestors 'none'; base-uri 'self'; form-action 'self'`（`npm run dev` のときだけ `script-src` に `'unsafe-eval'` を加える） |
| X-Content-Type-Options | `nosniff` |
| Referrer-Policy | `strict-origin-when-cross-origin` |
| Permissions-Policy | `camera=(self), microphone=(), geolocation=()` |

参考：[Stripe：Content Security Policy](https://docs.stripe.com/security/guide#content-security-policy)

### 3.3 GitHub Actions

`GUアプリ` フォルダを1つのGitリポジトリにし、`.github/workflows/` に次の4つを置く。

| ファイル | きっかけ | 内容 |
|---|---|---|
| `ci.yml` | pull request、mainへのpush | Backend：PostgreSQL 17のサービスコンテナを立て、`ruff check`・`pytest`・`pip-audit -r requirements.txt`。Frontend：`npm ci`・`npm run lint`・`npm run typecheck`・`npm run test`（Vitest）・`npm audit --audit-level=high`・`npm run build`。脆弱性検査でHigh以上が出たら失敗させる（N-07） |
| `deploy-backend.yml` | mainへのpush（`backend/**` の変更時）と手動実行 | `backend/` をZIPにして `azure/webapps-deploy` でBackendのWeb Appへデプロイ |
| `deploy-frontend.yml` | mainへのpush（`frontend/**` の変更時）と手動実行 | 3.2の手順でビルドし、FrontendのWeb Appへデプロイ。ビルド時の環境変数に `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`（Secret）と `NEXT_PUBLIC_DEV_TOOLS_ENABLED=true` を渡す |
| `jobs.yml` | `schedule`：`*/10 * * * *` と `0 18 * * *`（UTC＝日本時間3:00）、手動実行 | `curl -fsS -X POST -H "X-Job-Secret: ${{ secrets.JOB_SECRET }}" -H "Content-Type: application/json" -d '<本文>' $BACKEND_URL/internal/jobs/run`。10分ごとは本文 `{}`（J-01〜J-05）、毎日3:00は `{"jobs":["J-06","J-07"]}`。アプリが停止中でも、このアクセスで起動する |

- GitHub Actionsの定期実行は最短5分間隔で、混雑時は遅れることがある。公開リポジトリでは60日間リポジトリに動きがないと停止する。
- デプロイの認証は発行プロファイル（Publish Profile）を使う。各Web Appで「SCM基本認証の発行資格情報」を有効にし、発行プロファイルをGitHubのSecret（`AZURE_WEBAPP_PUBLISH_PROFILE_FRONTEND`、`AZURE_WEBAPP_PUBLISH_PROFILE_BACKEND`）に登録する。
- その他のSecret：`JOB_SECRET`、`BACKEND_URL`、`NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`（Frontendのビルド時に使う）。

### 3.4 リポジトリの作り方（既存の `gu-docs` の履歴を残す）

1. `gu-docs` の未コミットの変更をコミットする（`gu-docs` 内で `git add -A && git commit`）。
2. `GUアプリ` の外に `gu-docs` のコピーを作る（例：`~/gu-docs-history`）。
3. `GUアプリ` の `gu-docs` フォルダを一時的に別の場所へ退避する。`GUアプリ` で `git init` し、`.gitignore` だけを追加して最初のコミットを作る（`git subtree` は最初のコミットがないと失敗するため）。次に `git subtree add --prefix=gu-docs ~/gu-docs-history <ブランチ名>` で履歴ごと取り込む。
4. `.gitignore` に `node_modules/`、`.next/`、`.venv/`、`__pycache__/`、`.env`、`.env.local` を入れる。

履歴が不要なら、手順3の代わりに `gu-docs/.git` を削除して親フォルダで `git init` するだけでよい。

## 4. Stripe（テスト環境）

1. Stripeのアカウントでテスト環境（テストモード、またはサンドボックス）を使う。本番の有効化は行わない。
2. 設定の「決済手段」でカードだけを有効にする。
3. APIキー：公開キー `pk_test_…` をFrontend、秘密キー `sk_test_…` をBackendへ設定する。
4. Webhook：エンドポイント `https://app-pickup-back-<sfx>.azurewebsites.net/api/v1/payments/webhook`、イベント `payment_intent.amount_capturable_updated`、`payment_intent.requires_action`、`payment_intent.payment_failed`、`payment_intent.canceled`、`payment_intent.succeeded`、`refund.updated`、`charge.refunded`。表示された署名シークレット `whsec_…` をBackendへ設定する。
5. ローカル開発では Stripe CLI で `stripe listen --forward-to localhost:8000/api/v1/payments/webhook` を実行し、表示された `whsec_…` を `backend/.env` に設定する。
6. 試験用カード（有効期限は未来の任意の日付、セキュリティコードは任意の3桁）：

| 番号 | 結果 |
|---|---|
| 4242 4242 4242 4242 | 成功（追加認証なし） |
| 4000 0025 0000 3155 | 3Dセキュアの追加認証が必要 |
| 4000 0000 0000 9995 | 残高不足で拒否 |
| 4000 0000 0000 0002 | カード拒否 |

最新の試験用カードは [Stripe：テスト](https://docs.stripe.com/testing) で確認する。

## 6. デモ用の初期化

- 初回：`python -m app.cli seed`（01_DB設計 5章）。
- やり直し：`python -m app.cli reset-demo`（全テーブルを `TRUNCATE … CASCADE` し、`order_number_seq`・`pos_sale_number_seq` を `ALTER SEQUENCE … RESTART WITH 1` で戻してから、シードを入れ直す）。Azureでは BackendのWeb Appの「SSH」コンソールから `cd $APP_PATH && python -m app.cli reset-demo` を実行する。

## 7. ログ

- Python標準の `logging` で標準出力へJSON1行形式（`timestamp`、`level`、`requestId`、`path`、`status`、`durationMs`、`message`）を出す。App Serviceの「ログストリーム」で見る。
- 出してはならないもの：パスワード、トークン（JWT・リフレッシュ・QR）、手入力コード、カード情報、Stripeの秘密値、メール本文、メールアドレス（ユーザーIDで代える）。
- 例外はスタックトレースをログに出し、レスポンスには `INTERNAL_ERROR` と `traceId` だけを返す。
