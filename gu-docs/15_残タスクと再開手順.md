## 現在は自動公開しない

GitHubのRepository Variable `DEPLOYMENT_ENABLED` を `false` にします。Backend／Frontendのデプロイと定期ジョブの3ワークフローはいずれも、この値が `true` の場合だけ動きます。通常のCIはpush時に実行します。Azureや共有MySQLに新たな変更は加えません。

## 残タスク1：Stripeのテスト設定（Azure構築前でも可）

1. Stripeへログインして、使用するテスト環境／Sandboxを選びます。本番モードは使いません。[APIキー画面](https://dashboard.stripe.com/apikeys)で、同じテスト環境の公開キー `pk_test_...` と秘密キー `sk_test_...` を確認します。[公式キー説明](https://docs.stripe.com/keys)
2. ローカルのGit対象外ファイルを編集します。チャットや設計書に実際のキーを貼りません。

   | ファイル | 設定項目 | 入れる値 |
   |---|---|---|
   | `backend/.env` | `STRIPE_SECRET_KEY` | `sk_test_...` |
   | `frontend/.env.local` | `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` | `pk_test_...` |

3. [Stripe CLI](https://docs.stripe.com/cli)を用意し、ターミナルで次を実行します。

   ```sh
   stripe login
   stripe listen --forward-to http://localhost:8000/api/v1/payments/webhook
   ```

4. listen開始時に表示される `whsec_...` を、`backend/.env` の `STRIPE_WEBHOOK_SECRET` に設定します。これはAPIキーとは別の署名用シークレットです。CLIは転送中そのまま起動しておきます。[公式Webhook説明](https://docs.stripe.com/webhooks)
5. Stripeのテスト環境で、決済手段はカードのみを有効にします。
6. Backend／Frontendを再起動します。起動手順はREADMEを参照してください。Frontendの公開キーはビルドにも埋め込まれるため、本番形式で動かす場合は再ビルドします。
7. 架空の購入者で注文し、成功・カード拒否・3Dセキュアを確認します。カードは [Stripe公式テスト値](https://docs.stripe.com/testing) を使います。準備完了による一部確定、遅延取消による解放／返金、Webhookによる状態反映も確認します。

通常起動では実Stripe向けの処理を使います。テスト用のFake決済へ切り替える画面や環境変数はありません。注文や店員操作は接続中のDBを更新するため、ローカル専用DB等、試験対象を確認してから操作します。

## 残タスク2：Azureのアプリ環境を構築する

課題の共有MySQLと、今回これから作るWeb App／App Serviceプランは別です。DBが用意されていても、Frontend／Backendを公開するアプリ環境の構築が必要です。

1. `az login` でAzureへ再ログインし、対象サブスクリプションを確認します。以前の保存済み認証は期限切れでした。
2. リソース名・所有範囲・Free F1の利用可否を確認します。候補は `rg-pickup-app-shiochi`、`plan-pickup-shiochi`、`app-pickup-front-shiochi`、`app-pickup-back-shiochi`。まだ作成済みではありません。有料プランへ自動変更しません。
3. プロジェクト直下で、変更を行わない計画表示を確認します。

   ```sh
   backend/.venv/bin/python scripts/deploy_azure.py --create --configure-github --configure-only
   ```

4. Stripeテストキー、BackendのTLS付き `gu_app_shiochi` 接続設定、作成対象を確認し、**Azure構築を実施する段階でのみ**次を実行します。

   ```sh
   backend/.venv/bin/python scripts/deploy_azure.py --apply --create --configure-github --configure-only
   ```

   App Serviceの構築とアプリ設定・GitHub設定を行いますが、共有DBの作成・初期化はしません。configure-onlyでは定期ジョブを無効のままにします。失敗時も秘密値は出力しません。

## 残タスク3：初回デプロイと自動実行の有効化

1. Azure構築・設定後、GitHubのSettings → Secrets and variables → Actionsで次を確認します。

   - Secrets：`AZURE_WEBAPP_PUBLISH_PROFILE_BACKEND`、`AZURE_WEBAPP_PUBLISH_PROFILE_FRONTEND`、`NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`、`JOB_SECRET`、`BACKEND_URL`
   - Variables：`AZURE_WEBAPP_NAME_BACKEND`、`AZURE_WEBAPP_NAME_FRONTEND`、`DEPLOYMENT_ENABLED`

2. **デプロイを開始する段階でのみ** `DEPLOYMENT_ENABLED=true` にします。このフラグはデプロイと定期ジョブの両方を有効にするため、アプリ設定・接続先の準備が済んでから変更します。
3. GitHub Actionsの「Deploy Backend」「Deploy Frontend」を手動実行します。以後はmainのCI成功後にも自動実行されます。FrontendはLinux上で再ビルドし、Stripe公開キーを埋め込みます。
4. Backendの `/healthz`、FrontendのHTTPS表示とログイン・注文・準備・受取を確認します。
5. 公開したBackendのURLをStripeの [Webhook設定](https://dashboard.stripe.com/webhooks) に登録します。Snapshot形式を選び、受信イベントは次の7種類です。

   ```text
   payment_intent.amount_capturable_updated
   payment_intent.requires_action
   payment_intent.payment_failed
   payment_intent.canceled
   payment_intent.succeeded
   refund.updated
   charge.refunded
   ```

6. 公開先Webhookの署名シークレット `whsec_...` をAzure Backendの `STRIPE_WEBHOOK_SECRET` に設定して再起動します。ローカルCLI用のシークレットとは区別します。
7. 実Stripeの成功・拒否・3Dセキュア・確定・返金・Webhookを公開環境でも確認します。Scheduled Jobsの実行とjob_runsの記録も確認します。

## 残タスク4：受け入れ確認

- iPhone Safari／Android ChromeでカメラQR・手入力・画面操作を確認。
- 専用大量データで性能確認（3店舗・100商品・1,000 SKU、主要API各10回、起動済みで2秒以内）。共有Azureへの大量データ投入は別途対象・件数を確認。
- テスト仕様書のM-01〜M-14とUATを実施・記録。
- SMTPを使う場合のみ、設定と送信先を確認して実送信試験。現在の既定はsimulateで外部送信しません。

完了した項目は、この文書の該当箇所と実施結果を更新します。残タスクの存在をもって、未実施の試験やデプロイを完了扱いにはしません。
