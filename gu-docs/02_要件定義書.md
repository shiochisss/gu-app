## 1. はじめに

### 1.1 目的・文書の位置づけ

本書は、要求定義書の目的を満たすために必要な機能、外部との接点、非機能、セキュリティ、運用と確認項目を定義する。IEEE 830を参考に、「はじめに」「全体概要」「具体的な要件」を中心とした構成とする。規格への完全適合を宣言するものではない。

合意済みの業務ルールを具体化した要件と、文書化に際して補った提案を区別する。v0.3・v0.4では、基本設計・詳細設計の過程でプロジェクトオーナーが決定した事項（簡易POS・在庫管理、技術・設計条件、未決定事項T-01〜T-09の決定）を反映した。

本アプリは本番稼働させず、Azure上のテスト環境に構築して試験するまでを範囲とする（プロジェクトオーナー判断、2026年10月31日）。開発計画は別途作成せず、本書と基本設計書をもとに実装へ進む。

### 1.2 用語

| 用語 | 本書での意味 |
|---|---|
| 注文受付完了 | カードの利用枠確保に成功し、システムが注文を受け付けた時点 |
| 利用枠確保 | 後で支払いを確定できるよう、カードの利用枠を押さえること。売上確定とは別 |

| 準備完了予定時刻 | 注文前に示す、商品の準備が終わる見込みの具体的な日時 |
| 受け取り可能 | 商品の準備と決済確定がともに完了し、引き渡し条件を満たす状態 |
| 商品の単位 | 商品・色・サイズの組み合わせ。在庫はこの単位で区別する |
| 有効なQR | 対象注文を識別でき、指定店舗・支払・準備・取消・受取等の条件を満たす受け取りコード |
| 帳簿在庫 | 店舗にある販売用の現物の数としてシステムに記録された数 |
| EC確保数 | 受付中のEC注文が押さえている在庫の数 |
| 販売可能数 | 新しいEC注文・店頭販売に使える数。帳簿在庫からEC確保数を引いた数（0未満にはしない） |

## 2. 全体概要

### 2.1 対象と利用者

スマートフォンで空き時間に商品を選び、店舗で受け取る利用を中心とする。通常検索が標準であり、AI相談は追加候補とする。購入者、QRを託された代理受取人、準備・引き渡しを行う店員を扱う。店員は、店頭販売・入荷・棚卸・破損を簡易POSと在庫管理機能で記録し、EC注文と同じ店舗在庫を管理する。

配送・取り寄せ・物流管理・GU全体の再現は対象外。既存POSへの接続は前提としない。決済はStripeのテスト環境（テストモード）を用い、実際の金銭は扱わない。Next.jsとFastAPIによるWebアプリケーションとし、データベースはAzure Database for PostgreSQLを採用する。FrontendとBackendのソースコードを分け、それぞれ別のAzure App Service（Freeプラン）へデプロイする。詳細なサービス構成は基本設計書と詳細設計書で定める。

### 2.2 業務上の制約（合意済み）

- 1注文は数量合計10点まで。店舗の在庫から購入する。
- 注文受付完了から60分以内の準備完了を目標とする。
- 注文受付は閉店1時間前まで。初期運用モデルの準備担当は1人、受付順で作業する。
- 注文時にカードの利用枠を確保し、現物確保後に決済を確定する。
- 準備完了日の1週間後の閉店まで保管する。その日が休業日の場合は次の営業日の閉店まで延長する。
- QRを所持する代理人の受け取りを認め、代理人のログインや本人確認は求めない。
- EC注文と店頭販売は同じ店舗在庫を使う。店頭販売・入荷・棚卸・破損は簡易POSと在庫管理機能で記録する。

### 2.3 依存関係

予定時刻の精度は、在庫情報、先行注文の残作業、準備担当の作業時間に依存する。店頭の在庫変動は簡易POS・入荷・棚卸の登録に依存するため、店員が登録しないと帳簿在庫と現物がずれる。支払状態の確認はStripe、通知はメールサービスに依存する。時間の経過で動く処理（遅延の自動表示、期限切れ、決済結果の照合、メール送信）は、データを読むときの判定と、外部（GitHub Actions）から定期的に呼び出すジョブに依存する。Freeプランではアプリが常駐しないため、定期的な呼び出しが遅れると、メールの再送などの回収が遅れることがある。AI相談の有無はAPIの利用可否と残りの開発期間で判断する。

## 3. 具体的な要件

### 3.1 機能要件

以下は合意した業務方針をシステムの振る舞いに展開したもの。要件IDから要求ID・技術条件へ対応をたどれるようにする。

| ID | 機能要件 | 対応する要求 |
|---|---|---|
| F-01 | 店舗を選択でき、対象店舗の営業時間を確認できる | R-01、R-03 |
| F-02 | 選択店舗で在庫のある商品を検索・絞り込みでき、詳細で色・サイズ・数量を選べる。在庫ありは販売可能数が1以上であることを表す。検索はキーワード、絞り込みはカテゴリ・色・サイズ、並び順は新着・価格の安い順・高い順。価格は税込で表示する | R-01、R-02 |
| F-03 | 注文数量の合計が10点を超える場合は注文を受け付けず、修正を案内する | R-04 |
| F-04 | 注文前に準備完了予定日時、注文金額、受け取り店舗、受け取り期限の数え方、欠品時の希望、期限超過方針を確認できる | R-03、R-05、R-06、R-09 |
| F-05 | 営業時間と作業量に応じて受付可否を判定する。閉店1時間前ちょうどまで受け付け、それを過ぎた注文は受け付けない。作業量による受付基準と予定時刻の計算はT-01の決定に従う | R-03、R-04 |
| F-06 | カードの利用枠確保に成功してから注文受付完了とし、その日時と注文時の準備完了予定日時を保存する | R-03、R-05 |
| F-07 | 店員は受付順に対象注文と商品・色・サイズ・数量を確認し、現物の有無・状態の確認結果を記録できる | R-04、R-06 |
| F-08 | 欠品時の初期選択を全体キャンセルとする。一部購入の希望があれば用意できた商品だけを確定し、欠品と変更後の金額を通知する。全商品欠品時は全体キャンセルする。欠品した数量は帳簿在庫から減らし、再び販売可能にならないようにする | R-06 |
| F-09 | 現物確保後に用意できた商品の金額だけ決済を確定する。不要な利用枠は解放する。商品準備と決済確定の両方が完了した注文のみ受け取り可能にする | R-05、R-06、R-08 |
| F-10 | 店員が遅延を判断した時点で理由・新予定を登録し、購入者に知らせる。予定を過ぎても未完了なら自動で遅延を表示し、店舗に更新を求める。新予定が不明なら確認中とする | R-07 |
| F-11 | 店舗都合の遅延が発生した注文は受け取り前に無料キャンセルできる。遅延が解消して受け取り可能になった後も同様とする。未確定の利用枠は解放し、確定済みなら全額返金する。ただし、決済確定の処理中や、決済確定で問題が起きて店舗が確認している注文は、決済の状態が確定するまで購入者は取り消せない（店舗が対応する）。遅延のない注文の利用者都合の取消は初期実装では設けない（T-03） | R-07 |
| F-12 | 購入者は自分の注文詳細で最新状況、当初・更新後の予定、遅延理由、欠品内容、確定した受け取り期限、受け取り用QRを確認できる。QRは準備完了（受け取り可能）になってから表示し、購入者が再発行すると以前のQRは使えなくなる。QRと並べて、手入力用の6桁の受取コードを表示する | R-07、R-08、R-09、R-10 |
| F-13 | 受付完了・準備完了・遅延・欠品変更・取消・受取期限超過のメールを作成し、注文詳細へのリンクを含める。メールは送信時点の情報であることがわかるようにする。テスト環境では実際には送信せずに記録し、開発用の画面で内容を確認できる（設定により実送信に切り替えられる）。送信に失敗しても注文の状態は変えず、最初の送信を含めて最大5回まで送信を試みる | R-07 |
| F-14 | 店員はQR（読み取れない場合は注文番号と受取コードの手入力）で注文を照合し、指定店舗・支払済み・準備完了・未取消・未受取などの条件を確認する。読み取りだけでは受取済みにせず、実際の引き渡しを確定する | R-08 |
| F-15 | 同じQRのコピーや同時操作があっても、1注文の受け取り完了を二重に成立させない | R-08 |
| F-16 | 準備完了日の1週間後の店舗閉店時刻を受け取り期限として表示する。その日が休業日なら次の営業日の閉店時刻とする。期限を過ぎた注文は期限切れとし、店員が商品を棚に戻すまでは引き渡せる。棚に戻した時点で注文は終了し、商品は帳簿在庫へ戻り、代金は返金しない | R-09 |
| F-17 | 閲覧・検索はログイン不要。購入と自分の注文詳細・QR表示は会員登録・ログイン必須。店員操作には店員のログインを必須とする | R-10 |
| F-18 | QRを持つ代理受取人のログイン・氏名照合・身分証確認は不要とする。QRを持つだけでは購入者の注文履歴閲覧やキャンセルを許可しない | R-08、R-10 |
| F-19 | 店員は自店舗の新規注文の受付を停止・再開でき、営業時間・休業日を確認・登録できる。受付停止中も既存注文の準備・引き渡しは継続できる | R-03、R-04、O-01 |
| F-20 | 店員は簡易POSで、商品コードの読み取り・検索により店頭販売の明細を作り、売上を確定できる。売上の確定時に帳簿在庫を減らす。販売可能数を超える販売（EC注文で確保済みの商品を含む）は受け付けない。当日の売上は理由を付けて取り消せ、取消時は在庫を戻す。支払区分は記録のみとし、実際の決済・現金管理・レシート・返品は扱わない | SC-03、R-04 |
| F-21 | 店員は入荷、棚卸（実数の入力による差分調整）、破損・紛失を理由付きで登録できる。在庫の数量を直接書き換える操作は設けない | SC-03、O-02 |
| F-22 | 在庫の増減（入荷、店頭販売と取消、EC注文の出庫・欠品・取消や期限切れによる戻し、棚卸、破損）をすべて在庫履歴に記録する。新しいEC注文と店頭販売は販売可能数の範囲でのみ成立させる。欠品・棚卸・破損で帳簿在庫がEC確保数を下回った場合は、欠品見込みとして店員に表示する | SC-03、R-04、R-06 |

### 3.3 非機能・セキュリティ要件

60分の準備目標は店舗作業を含む業務目標であり、画面の応答速度とは区別する。

| ID | 要件 | 確認の観点 |
|---|---|---|
| N-01 操作性 | スマートフォンで主要な購入・状況確認操作を完了できる。予定時刻・金額・店舗・状態を、色だけに頼らず文字で確認できる。店員画面はPCの幅でもPOS・在庫操作を完了できる。対象はiPhone Safari・Android Chrome・PC Chromeの最新版 | 主要フローとエラー表示を確認 |
| N-02 性能 | 3店舗・100商品・1,000 SKUの試験データで、アプリ起動済みの状態で検索・注文詳細・QR照合・POS売上確定が2秒以内に応答する | 試験データで測定（Freeプランのため停止からの起動時間は対象外） |
| N-03 整合性 | 同時注文・同時の店頭販売で販売可能数を超えて成立させない。再送・再操作で二重注文、二重決済、二重返金、二重受取、二重売上を発生させない。画面に表示した金額・予定日時はBackendで再計算して照合する | 最後の在庫へのEC注文と店頭販売の同時操作、二重送信、処理途中の失敗で確認 |
| N-04 復旧性 | 決済や通知の失敗・結果不明を記録し、外部サービスの結果と照合して復旧できる | 成功した決済を失敗扱いで繰り返さないことを確認 |
| N-05 時刻 | 店舗の営業日と日時を一貫して扱う。初期対象の日本国内店舗では日本時間を使用する | 日付をまたぐ表示、締切、保管期限、休業日の境界を確認 |
| N-06 型・API定義 | FrontendはTypeScriptを使い、BackendのAPI定義（OpenAPI）から型を生成して入出力を一致させる。API一覧と入出力を基本設計書に示す | 型の生成手順と、APIの変更時に型が更新されることを確認 |
| N-07 依存関係 | 採用するOSSのバージョン、調査日、サポート期限を記録し、ロックファイルで固定する。依存関係の脆弱性検査を行う | 一覧と検査結果を確認 |
| S-01 権限 | 購入者は自分の注文だけを閲覧・操作できる。店員は担当店舗に許可された操作だけを行える | 他人の注文IDや他店舗の注文・在庫を指定しても拒否される |
| S-02 QR | QRを推測しにくくし、氏名・カード情報などを直接含めない。引き渡しの可否は最新の注文状態で判断する | 無効・コピー・取消済み・受取済み・棚戻し済みのコードを確認 |
| S-03 決済情報 | カード情報の入力はStripeの入力部品を使い、アプリにカード番号やセキュリティコードを保存しない。3Dセキュアの本人認証に対応する | 保存データ・ログ・画面を確認。テスト用カードで3Dセキュアの成功・失敗を確認 |
| S-04 秘密情報 | APIキーや認証情報を公開リポジトリ、購入者に配信するプログラム、ログへ含めない | 公開前と配信物の確認 |
| S-05 通信・入力 | 公開環境では暗号化通信を使い、重要な入力・価格・数量・操作権限をシステム側でも検証する | 画面上の制限を回避した要求でも不正な変更ができない |
| S-06 個人情報 | 購入・連絡に必要な情報（メールアドレス）に収集を絞り、ログに不要な個人情報や有効なQRを残さない。本番稼働しないため実在する顧客の情報は扱わない | 収集項目はメールアドレスとパスワードのみ。保存期間は定めず、試験の区切りでデモ初期化により削除する |
| S-07 BFF・CORS | ブラウザはBFFを経由してBackendを呼び出す。BackendはBFFとの共有秘密を持つ要求だけを受け付け、ブラウザからの直接の呼び出し（CORS）は許可しない | 許可していないオリジン・秘密のない要求を拒否する |
| S-08 API文書 | 本番相当の環境ではSwagger UIとOpenAPI定義の公開ルートを無効にする | 該当URLが取得できないことを確認 |
| S-09 データアクセス | ORMまたはパラメータ化クエリを使い、利用者入力をSQL文字列へ連結しない | SQL注入文字列がSQLとして実行されない |

### 3.4 運用要件

| ID | 運用 | 決めること |
|---|---|---|
| O-01 開店・受付 | 営業時間・休業日・受付状態を管理し、準備担当が対応できないときは新規受付を停止できる（F-19） | なし（店員が操作し、再開も店員が判断） |

## 4. 主要ユースケース

### UC-01 店舗の商品を探す

- 主体：購入者。ログイン不要。
- 開始条件：店舗・商品・在庫情報が登録されている。
- 基本の流れ：店舗を選択 → 在庫のある商品を検索・絞り込み → 詳細で色・サイズ・数量を選択。
- 例外：該当商品や希望する組み合わせの在庫がなければ、その状態を表示して選び直せる。
- 結果：注文したい商品を選択できる。閲覧時点で在庫があっても注文成立は確約しない。
- 対応：F-01、F-02、F-17。

### UC-02 予定時刻を確認して注文する

- 主体：購入者。外部関係者：決済サービス（Stripe）。
- 開始条件：店舗と商品を選択済み。購入時はログインしている。
- 基本の流れ：数量・在庫・受付可否を確認 → 予定時刻・金額・期限と条件を確認 → 欠品時の希望を選択 → 支払手続き（必要に応じて3Dセキュア） → 利用枠確保と注文受付を成立させる → 受付結果を表示。
- 例外：10点超過、受付締切後、受付停止中、在庫不足、作業枠不足では修正・受付不可を案内する。利用枠確保の失敗時は受付完了とせず、押さえた在庫を戻す。結果不明時は「支払確認中」と表示し、定期処理が結果を照合する。
- 結果：当初の予定時刻と受付日時が記録される。在庫・作業枠・決済を矛盾なく確定する手順は基本設計書で定める。
- 対応：F-03〜F-06、F-17、F-19。

### UC-03 現物を確保して準備を完了する

- 主体：ログインした店員。外部関係者：決済・メールサービス。
- 開始条件：受け付けた未取消の注文がある。
- 基本の流れ：受付順に注文を確認 → 現物の色・サイズ・数量・状態を確認し取り分ける → 用意できた金額の決済を確定 → 準備完了を記録 → 受け取り可能にして期限を確定し、メール通知。
- 例外：欠品時は注文時の希望に従い、欠品数量を帳簿在庫から減らす。全部欠品なら全体キャンセル。一部購入なら不足分を除いて金額を確定する。決済確定に成功しなければ受け取り可能にしない。
- 結果：受け取り可能、キャンセル、または対応が必要な状態になる。
- 対応：F-07〜F-09、F-13、F-16、F-22。

### UC-04 遅延を知り、待つかキャンセルする

- 主体：購入者、店員。
- 開始条件：店舗が遅延を判断した、または予定時刻を過ぎても準備が完了していない。
- 基本の流れ：遅延を表示し店舗が理由・新予定を更新 → 購入者へ通知 → 購入者が最新情報を確認 → 継続して待つか、受け取り前に無料キャンセルする。
- 例外：新予定が不明なら確認中とする。決済確定前の取消は利用枠解放、確定後は全額返金。返金失敗は処理済みと見なさず対応する。
- 結果：注文が継続するか、取消・利用枠解放または返金へ進む。当初の予定は保存する。
- 対応：F-10〜F-13。

### UC-05 本人または代理人がQRで受け取る

- 主体：QR所持者、ログインした店員。
- 開始条件：対象注文が受け取り可能、または期限切れだが商品が棚に戻されていない。
- 基本の流れ：QRを提示 → 店員が読み取り注文を照合 → 指定店舗・支払・準備・取消・受取状態を確認 → 商品を渡す → 店員が受け取り完了を確定する。
- 例外：別店舗、無効QR、未準備、未決済、取消済み、受取済み、棚戻し済みでは引き渡しを認めない。重複操作でも受取完了は一度だけ成立させる。
- 結果：受け取り済みとなり、同じQRやコピーを再利用できない。提示者の氏名照合・ログインは不要。
- 対応：F-14〜F-18。

### UC-06 店頭販売を登録する

- 主体：ログインした店員。
- 開始条件：店舗・商品・在庫が登録されている。
- 基本の流れ：商品コードを読み取る、または検索して明細を作る → 数量を入力 → 合計と販売可能数を確認 → 支払区分を選び売上を確定 → 帳簿在庫が減る。
- 例外：販売可能数を超える明細（EC注文で確保済みの商品を含む）は売上を確定できず、理由を表示する。誤登録は当日中に理由を付けて取り消し、在庫を戻す。
- 結果：売上と在庫履歴が記録され、EC注文の販売可能数に反映される。
- 対応：F-20、F-22。

### UC-07 入荷・在庫を調整する

- 主体：ログインした店員。
- 開始条件：店舗・商品・在庫が登録されている。
- 基本の流れ：在庫一覧で商品を選ぶ → 入荷数、棚卸の実数、破損・紛失の数を理由付きで登録 → 帳簿在庫と在庫履歴が更新される。
- 例外：調整後の帳簿在庫がEC確保数を下回る場合は欠品見込みを警告し、確定後は注文一覧と在庫一覧に表示する。帳簿在庫を0未満にする登録は受け付けない。
- 結果：帳簿在庫が現物に合わせて更新され、履歴が残る。
- 対応：F-21、F-22。

### UC-08 期限切れの商品を処理する

- 主体：ログインした店員。
- 開始条件：受け取り期限を過ぎ、受け取られていない注文がある。
- 基本の流れ：注文一覧の期限切れ注文を確認 → 来店があればQRで引き渡す。来店がなければ商品を棚に戻し、システムで「棚に戻す」を確定する。
- 例外：棚に戻した後のQRは受け付けない。
- 結果：注文が終了し、商品は帳簿在庫へ戻る。代金は返金しない。
- 対応：F-16、F-22。

## 5. 情報と状態の整理

### 5.1 記録が必要な情報

| 情報 | 主な内容・目的 |
|---|---|
| 店舗 | 店舗識別子、営業時間、休業日、受付状態 |
| 商品・在庫 | 商品、色、サイズ、価格、帳簿在庫、EC確保数 |
| 在庫履歴 | 増減の種類（入荷、店頭販売と取消、EC出庫・欠品・戻し、棚卸、破損）、増減数、理由、操作者、日時 |
| 注文 | 購入者、店舗、商品明細、数量、注文時金額、確定金額、欠品時の希望 |
| 時刻 | 受付日時、当初予定、変更後の予定、実際の準備完了、受け取り期限、受け取り日時 |
| 決済 | 外部取引の識別子、利用枠確保・決済確定・解放・返金の金額と結果 |
| 受け取り | QRと注文の対応、利用状態、引き渡しを確定した店員 |
| 店頭売上 | 売上番号、店舗、店員、明細、合計、支払区分、取消の有無と理由 |
| 履歴 | 欠品・遅延理由、状態変更と操作者、通知の成否 |

当初予定と実績を保存することは合意済み。テーブル設計は基本設計書のER図で定める。

### 5.2 状態を混同しないための方針

注文の進行（受付・準備・受け取り等）、支払いの状態（利用枠確保・決済確定・返金等）、遅延の有無、在庫確保の状態を区別する。「キャンセル済み」でも返金が完了したとは限らず、「商品を取り分け済み」でも決済が未完了なら引き渡せない。状態の一覧と遷移条件は基本設計書で定める。
