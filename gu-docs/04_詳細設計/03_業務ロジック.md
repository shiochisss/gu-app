## 2. 営業日と時刻

### 2.1 ある日の営業時間

関数 `get_business_hours(store, date) -> (opens_at, closes_at) | CLOSED`：

1. `business_hours` に `(store_id, date)` の行があれば、`closed=true` なら CLOSED、そうでなければその行の `opens_at`・`closes_at`。
2. 行がなければ、`date` のISO曜日が `stores.regular_closed_weekdays` に含まれれば CLOSED、そうでなければ `default_opens_at`・`default_closes_at`。
3. 時刻は `Asia/Tokyo` のローカル時刻として `date` と結合し、UTCへ変換し、DBにはdatetime(6)で保存する。

### 2.2 受付締切

注文要求（API-08見積もり、API-09注文）を受信した時刻 `now` について、`today = now を Asia/Tokyo に変換した日付` とする。

- 今日が CLOSED → `ORDER_CLOSED`
- `now > closes_at(today) − 60分` → `ORDER_CLOSED`（ちょうど `closes_at − 60分` は受付可）
- 開店前の注文は受け付ける。作業開始時刻を開店時刻とする（3.1）。

### 2.3 受取期限

関数 `compute_pickup_deadline(store, ready_at)`：

1. `d = (ready_at を Asia/Tokyo に変換した日付) + 7日`
2. `d` が CLOSED なら `d` を1日ずつ進める（最大31日。超えたら例外 `NO_BUSINESS_DAY` として500）。
3. `d` の `closes_at` を受取期限とする。

例：9月7日準備完了 → 9月14日の閉店時刻。9月14日が休業日なら9月15日以降の最初の営業日の閉店時刻。

## 3. 見積もりと注文受付

### 3.1 作業時間と予定時刻

- 作業時間 `work_minutes = 2 × 合計点数 + 10`
- **列の順番**：店舗の作業は「見積もりを作った時刻」の順に並ぶとみなす。注文の順番はその注文の元になった見積もり（`orders.estimate_id`）の `created_at` で決まる。
- 関数 `compute_ready_at(store, work_minutes, base_time, 自分の位置, exclude_estimate_ids)`：
  - 作業開始時刻 `base = max(base_time, 今日の開店時刻)`
  - 先行作業 `queue_minutes` ＝ 同じ店舗で、元の見積もりの `created_at` が今日（Asia/Tokyo）で、かつ列の順番が自分より前のものについて、次の `work_minutes` の合計（`exclude_estimate_id` の見積もりとその注文は除く）。「自分より前」は、見積もり（API-08）では `created_at <= now`、注文時の再計算（API-09）では `(created_at, id) < (自分の見積もりの created_at, 自分の見積もりの id)`（同じ時刻なら id の小さい方を先とする）
    - `orders.status IN (RECEIVED, PREPARING, ACTION_REQUIRED)` の注文
    - `orders.status = PENDING_PAYMENT AND hold_expires_at > now` の注文
    - `order_estimates.status = 'HELD' AND expires_at > now` の見積もり
  - 予定時刻 `ready = base + queue_minutes + work_minutes + 15分` を、秒以下を切り上げて分単位にする。60分の判定（3.2の8）は切り上げた後の値で行う。
- 見積もり（API-08）では `base_time = now`、`exclude_estimate_id = 同じ利用者・同じ店舗の HELD の見積もり（再見積もりで自分の前回分を数えないため）`。注文時の再計算（API-09）では `base_time = estimate.created_at`、`exclude_estimate_id = 自分の見積もり` とする。こうすると、見積もりの後に他の人が見積もり・注文しても、また時間がたつだけでも、自分の予定は遅くならない。
- 前日以前に受け付けて残っている注文は先行作業に数えない（翌日に持ち越した作業は店員が遅延として扱う）。

### 3.2 受付判定（上から順に判定し、最初に該当したエラーを返す）

| 順 | 条件 | エラーコード |
|---|---|---|
| 1 | 店舗が存在しない | `STORE_NOT_FOUND`（404） |
| 2 | 明細が空、数量が1未満、同じSKUが重複 | `VALIDATION_ERROR`（400） |
| 3 | 合計点数 > 10 | `ORDER_LIMIT_EXCEEDED`（422） |
| 4 | SKUが存在しない、非アクティブ、またはその店舗の在庫行がない | `PRODUCT_NOT_FOUND`（404） |
| 5 | `stores.accepting_orders = false` | `STORE_NOT_ACCEPTING`（422） |
| 6 | 2.2の受付締切 | `ORDER_CLOSED`（422） |
| 7 | いずれかの明細で 数量 > 販売可能数 | `OUT_OF_STOCK`（422、不足明細を `details` に入れる） |
| 8 | `ready − base > 60分`（base は作業開始時刻。開店前の注文は開店時刻から数える）または `ready > 今日の閉店 − 15分` | `CAPACITY_FULL`（422） |

### 3.3 リクエストハッシュ

`request_hash = SHA-256(正規化JSON)`。正規化JSONは `{"storeId":..., "items":[{"productVariantId":..., "quantity":...}], "shortagePolicy":...}` で、items を productVariantId の昇順に並べ、キーを辞書順にし、空白なしで出力したもの（`json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False)`）。見積もりと注文の明細が同じかの照合に使う（Idempotency-Keyの判定は13章の本文全体のハッシュを使う）。

### 3.4 見積もり作成（API-08）

1つのトランザクションで行う。外部サービスは呼ばない。

1. 3.2の1〜4を判定する。
2. 店舗行を `SELECT … FOR UPDATE` でロックする（作業枠の計算を店舗単位で直列化するため）。
3. 3.2の5〜8を判定する（予定は3.1の見積もり時の条件で計算。同じ利用者・同じ店舗の HELD の見積もりは先行作業から除く）。不可なら見積もりを保存せず、前回の見積もりもそのまま残し、`accepted=false` と理由をレスポンス200で返す（エラーにしない。画面で理由を表示するため）。ただし1〜4は通常のエラーとして返す。
4. 可なら、同じ利用者・同じ店舗の HELD の見積もりをすべて `EXPIRED` にし（1人が作業枠を複数押さえないため）、新しい見積もりを `HELD`、`created_at = now`、`expires_at = now + 10分` で保存して `accepted=true` を返す。

期限切れの PENDING_PAYMENT 注文の後始末（Stripeへの照会を伴う）はこの処理では行わず、J-02に任せる。期限切れの仮確保は3.1の先行作業には数えないが、在庫の `reserved_quantity` にはJ-02が解放するまで残る。

### 3.5 注文作成（API-09）

決済サービスへの呼び出しをトランザクションの外で行うため、3つの段階に分ける。

**段階1（トランザクション1）**

1. Idempotency-Keyの処理（13章）。
2. 店舗行を `FOR UPDATE` でロックし、次に `estimateId` の見積もりを `FOR UPDATE` で取得する（ロック順序は3.7）。次の場合は409 `ESTIMATE_EXPIRED`：存在しない、他人の見積もり、別の店舗、`status != HELD`、`expires_at <= now`。
3. リクエストの `request_hash` が見積もりと一致しなければ409 `CALCULATION_CHANGED`。
4. `agreedToPickupTerms != true` なら422 `TERMS_NOT_AGREED`。
5. 3.2の5・6を `now` で再判定する。
6. 明細の在庫行を `inventory_id` の昇順に `FOR UPDATE` でロックし、3.2の7を再判定する。
7. 金額を再計算する。`clientTotalAmountYen` と一致しなければ409 `CALCULATION_CHANGED`（最新値を返す）。
8. 予定時刻を3.1の注文時の条件で再計算する。再計算値が `estimate.estimated_ready_at + 5分` より後なら409 `CALCULATION_CHANGED`（通常は起きない。見積もり後に店員が今日の開店時刻を遅らせた場合などに起きる）。`clientEstimatedReadyAt` が `estimate.estimated_ready_at` と一致しなければ409 `CALCULATION_CHANGED`。
9. 次を登録する。
   - `orders`：status `PENDING_PAYMENT`、`original_ready_at = estimate.estimated_ready_at`、`hold_expires_at = now + 15分`、`pickup_terms_agreed_at = now`、`order_number` 採番
   - `order_items`：SKU・商品名・色・サイズ・単価のスナップショット
   - `inventory_reservations`：status `HELD`、`expires_at = hold_expires_at`。在庫行の `reserved_quantity += 数量`
   - `payments`：status `AUTHORIZING`、`last_operation = AUTHORIZE`、`operation_attempt = 1`、`authorized_amount_yen = 合計`、`operation_started_at = now`
   - `order_estimates.status = USED`
   - 監査履歴 `ORDER_REQUESTED`
10. コミットする。

段階1のコミット後は、どんな例外が起きても5xxで終わらせない。例外は捕捉してログに出し、決済を UNKNOWN にして202（`paymentStatus: UNKNOWN`、`orderId` 付き）を返す（冪等キーの記録も残す。13章）。利用者が同じ内容で再注文して二重に与信することを防ぐため。

**段階2（トランザクション外）**

Stripeで PaymentIntent を作成・確定する（5.2のAUTHORIZE）。

**段階3（トランザクション2）**

結果を5.3の `apply_payment_intent` で反映する。

| Stripeの結果 | payments | orders | レスポンス |
|---|---|---|---|
| `requires_capture` | AUTHORIZED | RECEIVED（4章の受付処理） | 201 |
| `requires_action` | REQUIRES_ACTION | PENDING_PAYMENT のまま | 202（`nextAction.clientSecret`） |
| カード拒否（CardError）または `requires_payment_method` | FAILED、`failure_code` | NOT_ACCEPTED（在庫解放） | 422 `PAYMENT_DECLINED` |
| 結果不明（5.1の「結果不明」） | UNKNOWN | PENDING_PAYMENT のまま | 202（`paymentStatus: UNKNOWN`） |
| Stripeが失敗の確定したエラー応答（5.1の「失敗」） | FAILED（`failure_code` にエラーの種類） | NOT_ACCEPTED（在庫解放） | 422 `PAYMENT_DECLINED` |

### 3.6 追加認証（3Dセキュア）後の確認

画面は `stripe.handleNextAction` の完了後に API-36（支払結果の確認）を呼ぶ。API-36はStripeから PaymentIntent を取得し、`apply_payment_intent` で反映した結果を返す。Webhookでも同じ反映を行うため、どちらが先でも結果は同じになる。PaymentIntent ID が未保存（作成の応答を受け取れなかった）の場合、API-36は Stripe を呼ばずに現在の状態を返す（J-03が回収する）。

### 3.7 ロックの順序

デッドロックを防ぐため、1つのトランザクションで複数の行をロックするときは必ず次の順にする：`stores` → `order_estimates` → `orders` → `payments` → `inventory_reservations` → `inventories`（`inventory_id` の昇順）→ `pickup_tokens`。ロックは `SELECT … FOR UPDATE` で取り、不要な行はロックしない。

## 4. 注文の状態遷移

この表にない遷移は行わない。遷移の前に必ず `version` を確認し、更新時に `version += 1` する。

| No | 遷移 | きっかけ | 条件 | 同時に行うこと |
|---|---|---|---|---|
| T1 | なし → PENDING_PAYMENT | API-09 段階1 | 3.5 | 3.5 段階1の登録 |
| T2 | PENDING_PAYMENT → RECEIVED | 利用枠確保の成功（API-09、API-36、Webhook、J-02、J-03） | payments が AUTHORIZED | `accepted_at = now`、確保を CONFIRMED、`expires_at = NULL`、メール `ORDER_ACCEPTED`、監査 `ORDER_ACCEPTED` |
| T3 | PENDING_PAYMENT → NOT_ACCEPTED | 利用枠確保の失敗、または仮確保の期限切れ（J-02） | payments が FAILED、または期限切れで PaymentIntent を取消済み | 確保を RELEASED、`reserved_quantity −= 数量`、監査 `ORDER_NOT_ACCEPTED`（メールは送らない） |
| T4 | RECEIVED → PREPARING | API-15 | 自店舗 | `preparation_started_at = now`、監査 |
| T5 | RECEIVED / PREPARING / READY → CANCELLED | API-12（購入者） | `delay_occurred = true`、かつ決済が RECEIVED・PREPARING なら AUTHORIZED、READY なら CAPTURED | 7.3 |
| T6 | PREPARING → CANCELLED | API-16（欠品） | 決済が AUTHORIZED、かつ全明細が全数欠品、または `shortage_policy = CANCEL_ALL` で欠品あり | 6.3、決済は解放（5.2 RELEASE）、メール `CANCELLED` |
| T7 | PREPARING → READY | API-18（決済確定の成功）、J-03 | payments が CAPTURED | 6.4、`ready_at = now`、受取期限（2.3）、`is_delayed = false`、QRトークン発行（9.5）、メール `READY` |
| T8 | PREPARING → ACTION_REQUIRED | API-18で決済確定が失敗・結果不明 | | 監査 `CAPTURE_FAILED` |
| T9 | ACTION_REQUIRED → READY | J-03・API-18再実行で決済確定を確認 | payments が CAPTURED | T7と同じ |
| T10 | ACTION_REQUIRED → PREPARING | 管理コマンド `orders resume` | 決済が FAILED(CAPTURE) で、Stripeから取得した PaymentIntent が `requires_capture` | 決済を AUTHORIZED に戻す（`operation_attempt` はそのまま） | |
| T11 | ACTION_REQUIRED → CANCELLED | 管理コマンド `orders cancel` | 決済が UNKNOWN・処理中でない（先に `payments reconcile` で確定させる） | 確保（CONFIRMED）を解放（6.2）。決済が AUTHORIZED、または FAILED(CAPTURE) で PaymentIntent が `requires_capture` なら RELEASE、CAPTURED なら REFUND、それ以外（与信が失効済み）は決済の操作なし。`cancel_reason_code = ADMIN`、監査の reason にコマンドで指定した文を記録、メール `CANCELLED` |
| T12 | READY / EXPIRED → PICKED_UP | API-20 | 9.6の判定、payments が CAPTURED | `picked_up_at`、`handed_over_by`、トークン `used_at`、`is_delayed = false`、監査 `HANDED_OVER` |
| T13 | READY → EXPIRED | 8章の同期処理、J-05 | `now > pickup_deadline_at` | `expired_at = now`、メール `EXPIRED`、監査 |
| T14 | EXPIRED → EXPIRED_RETURNED | API-35 | 自店舗 | 6.5、トークン `revoked_at = now`・`revoked_reason = RETURNED`、監査 `RETURNED_TO_STOCK` |

購入者が取り消せる条件（`canCancel`）：`delay_occurred = true`、かつ「status が RECEIVED・PREPARING で決済が AUTHORIZED」または「status が READY で決済が CAPTURED」。遅延のない注文の取消（利用者都合）は設けない（要件定義書 T-03）。ACTION_REQUIRED（決済確定で問題が起きている注文）は、決済の状態が確定しないと安全に取り消せないため購入者は取り消せず、店舗（管理コマンド）が対応する。

すべての状態遷移APIは、注文行をロックした後に ①`version` 不一致 → 409 `CONFLICTING_UPDATE` ②8章の同期（時間で変わる状態の確定。ここで version が上がっても①はやり直さない）③状態・決済の条件を満たさない → 409 `INVALID_STATE`（API-12は422 `CANCEL_NOT_ALLOWED`）④入力値の検証、の順に判定する。同時に操作した場合、後から来た側は①で409になる。

## 5. 決済（Stripe テストモード）

### 5.1 前提

- `stripe` Python SDK（v16系）を使い、APIバージョンはSDKの既定値とする。秘密キーは環境変数 `STRIPE_SECRET_KEY`（`sk_test_...`）。
- 通貨は `jpy`（小数なし通貨。金額は円の整数をそのまま渡す）。
- Stripeダッシュボード（テスト環境）で、決済手段はカードだけを有効にする（05_インフラ・設定 4章）。
- 作成・変更の呼び出し（create・capture・cancel・refund）に `idempotency_key` を付ける（取得・検索には付けない）。形式：`{payment_id}:{操作}:{payments.operation_attempt}`。
  - 新しい操作を始めるとき：前回と違う種類の操作なら `last_operation = 操作`・`operation_attempt = 1`、同じ種類（例：失敗した確定のやり直し）なら `operation_attempt += 1`。
  - 応答を受け取れなかった（通信エラー・タイムアウト）ときの再試行：同じ `operation_attempt`（同じキー）を使う。Stripeは同じキーの要求に最初の結果を返すため、二重に処理されない。
  - Stripeがエラー応答を返した、または Refund が `failed` になったときの再試行：`operation_attempt += 1` して新しいキーを使う（同じキーでは同じエラーが返り続けるため。[Stripe：Idempotent requests](https://docs.stripe.com/api/idempotent_requests)）。
- PaymentIntent の `metadata` に `order_id`、`order_number`、`store_code` を入れる。PaymentIntent ID を保存できなかった場合は `PaymentIntent.search(query="metadata['order_id']:'<注文ID>'")` で探す（Search APIは反映まで最大1分程度かかることがあるため、作成から5分以上たったものだけに使う）。
- タイムアウトは10秒。例外の扱い：

| 区分 | 例外 | 扱い |
|---|---|---|
| 拒否 | `CardError` | 失敗が確定（カード拒否） |
| 失敗 | `InvalidRequestError`、`AuthenticationError`、`PermissionError`、`IdempotencyError` | 失敗が確定（Stripeが要求を処理しなかった） |
| 結果不明 | `APIConnectionError`、タイムアウト、`APIError`（Stripe側の5xx）、`RateLimitError` | 処理されたか分からない。UNKNOWN にし、J-03が照合する |

- 再試行は1つの操作につき `operation_attempt` が5になるまでとする。上限に達したら再試行をやめ、WARNINGログを出して管理コマンドでの対応に回す。

### 5.2 操作

| 操作 | Stripe API | パラメータ | 呼ぶ場所 |
|---|---|---|---|
| AUTHORIZE | `PaymentIntent.create` | `amount=合計`、`currency="jpy"`、`capture_method="manual"`、`confirm=True`、`confirmation_token=画面から受け取ったID`、`automatic_payment_methods={"enabled": True, "allow_redirects": "never"}`、`metadata` | API-09 段階2 |
| REFRESH | `PaymentIntent.retrieve`（IDがなければ `PaymentIntent.search`） | | API-36、Webhook、J-02、J-03 |
| CAPTURE | `PaymentIntent.capture` | `amount_to_capture=確定額`（一部確定時、残額はStripeが自動で解放する） | API-18、J-03 |
| RELEASE | `PaymentIntent.cancel` | `cancellation_reason="abandoned"` | API-12、API-16、J-02 |
| REFUND | `Refund.create` | `payment_intent=ID`、`amount=確定額の全額` | API-12（READYの取消） |

AUTHORIZEは再実行しない（ConfirmationTokenは一度しか使えず、期限切れ後に与信が成立するのを防ぐため）。段階2で応答を受け取れず PaymentIntent ID が未保存の場合は、J-03・J-02が search で探して反映する。見つからなければ与信は成立していないとみなす。

### 5.3 PaymentIntentの状態の反映（`apply_payment_intent`）

| Stripeの `status` | 現在の payments.status | 反映後 | 注文への処理 |
|---|---|---|---|
| `requires_action` | AUTHORIZING・UNKNOWN（AUTHORIZE） | REQUIRES_ACTION | なし |
| `requires_capture` | AUTHORIZING・REQUIRES_ACTION・UNKNOWN（AUTHORIZE） | AUTHORIZED（`authorized_confirmed = true`） | 注文が PENDING_PAYMENT で `hold_expires_at > now` なら T2。期限切れなら J-02 の取消手順へ |
| `requires_capture` | AUTHORIZED | 変えない（重複受信） | なし |
| `requires_capture` | CAPTURING・UNKNOWN（CAPTURE） | 変えない（確定がStripeに届いていない） | J-03が同じキーで capture を再送する |
| `requires_capture` | RELEASING・UNKNOWN（RELEASE） | 変えない | J-03が同じキーで cancel を再送する |
| `succeeded` | CAPTURING・UNKNOWN（CAPTURE）・FAILED（CAPTURE） | CAPTURED（`captured_amount_yen = amount_received`、`released_amount_yen = authorized − captured`） | 注文が PREPARING・ACTION_REQUIRED なら T7・T9。注文が CANCELLED なら REFUND を開始する（防御的な処理） |
| `canceled` | RELEASING・UNKNOWN（RELEASE）・FAILED（RELEASE） | `authorized_confirmed = true` なら RELEASED（`released_amount_yen = authorized`）、false なら FAILED（`failure_code = CANCELED_BEFORE_AUTHORIZATION`、released 0）。どちらもこれで終わり（J-03の対象外） | 注文が PENDING_PAYMENT なら T3 |
| `canceled` | AUTHORIZING・REQUIRES_ACTION・UNKNOWN（AUTHORIZE） | FAILED（`failure_code = CANCELED`） | 注文が PENDING_PAYMENT なら T3 |
| `requires_payment_method` | AUTHORIZING・REQUIRES_ACTION・UNKNOWN（AUTHORIZE） | FAILED（`failure_code = last_payment_error.decline_code` または `code`） | 注文が PENDING_PAYMENT なら T3 |
| `processing`、`requires_confirmation` | いずれも | 変えない | なし |

上の表にない組み合わせ（例：すでに CAPTURED の決済に `requires_capture` が届いた）は、古いイベントとして無視し、WARNINGログを出す。

Refund の `status`（REFUNDING・UNKNOWN(REFUND)・FAILED(REFUND) の決済に対して）：`succeeded` → REFUNDED（`refunded_amount_yen = amount`）、`pending`・`requires_action` → REFUNDING のまま、`failed`・`canceled` → FAILED（`last_operation = REFUND`）。FAILED(REFUND) は J-03 が `operation_attempt += 1` して再実行する。

### 5.4 Webhook（API-13）

エンドポイントは `async def` で定義し、`await request.body()` で生の本文を読む（署名検証に必要）。署名検証の後の処理は `run_in_threadpool` で同期の関数を呼ぶ。

1. ヘッダー `Stripe-Signature` を `stripe.Webhook.construct_event(payload, sig, STRIPE_WEBHOOK_SECRET)` で検証する。失敗したら400を返し、何もしない。
2. 受信の記録（トランザクション1、すぐにコミット）：`payment_events` への挿入をSAVEPOINT内で試み、同じprovider_event_idの重複（MySQLエラー1062）だけ既存行として扱う。他のDBエラーは再送可能な失敗とする。続いて対象行を `SELECT ... FOR UPDATE` し、処理済み（processed_atがNULLでなく、resultがERROR以外）、またはprocessing_untilがnow以上なら200で終了する。それ以外はprocessing_untilをnow＋2分へ更新する。判定・更新を同じトランザクション内で行い、処理を確保したらコミットする。
3. 処理対象のイベント：`payment_intent.amount_capturable_updated`、`payment_intent.requires_action`、`payment_intent.payment_failed`、`payment_intent.canceled`、`payment_intent.succeeded`、`refund.updated`、`charge.refunded`。それ以外は `result = IGNORED` を記録して200。
4. トランザクションの外で、イベント本文の値は信用せずStripeから取得し直す。
   - `payment_intent.*`：`data.object.id` の PaymentIntent を取得する。
   - `refund.updated`：`data.object.id` の Refund を取得する。
   - `charge.refunded`：`data.object.payment_intent` から `Refund.list(payment_intent=…)` を取得し、`payments.provider_refund_id` と一致する Refund を使う（未保存なら最新の Refund を使い、IDを保存する）。
5. トランザクション2：対応する payments を `provider_payment_intent_id` で探し、なければ PaymentIntent の `metadata.order_id` の注文の payments を使う（このとき `provider_payment_intent_id` を保存する）。どちらもなければ `IGNORED`。見つかれば5.3で反映し、`processed_at`・`result = APPLIED`・`processing_until = NULL` を記録してコミットし、200を返す。5.3で返金の開始が必要になった場合は、決済を REFUNDING にしてコミットした後、トランザクションの外で Refund を作成し、トランザクション3で結果を反映する。
6. 4・5で例外が起きたらトランザクション2をロールバックし、別のトランザクションで `result = ERROR`・`processing_until = NULL` を記録して500を返す（Stripeが再送し、2で再処理される）。

## 6. 在庫の操作

すべて在庫行を `inventory_id` の昇順で `SELECT … FOR UPDATE` してから行い（3.7の順序）、`inventories.version += 1`、`updated_at = now` とする。帳簿在庫が変わる操作は必ず `inventory_transactions` を1行追加する（`on_hand_after` は更新後の値）。

### 6.1 新しい需要（EC仮確保・POS販売）

- 販売可能数 `available = max(0, on_hand − reserved)` を計算し、`数量 > available` なら不可（EC：`OUT_OF_STOCK` 422、POS：`INSUFFICIENT_STOCK` 409）。
- EC仮確保：`reserved += 数量`（在庫履歴なし）。
- POS販売：`on_hand −= 数量`、履歴 `POS_SALE`（delta −数量、reference_type `POS_SALE`・reference_id 売上ID）。

在庫履歴の参照先：EC_PICKUP_OUT・EC_SHORTAGE・EC_CANCEL_RETURN・EC_EXPIRED_RETURN は reference_type `ORDER_ITEM`・reference_id 注文明細ID。POS_SALE・POS_VOID は `POS_SALE`・売上ID。INITIAL・RECEIVE・STOCKTAKE・DAMAGE は参照なし（NULL）。API-30の referenceLabel は、ORDER_ITEM なら注文番号、POS_SALE なら売上番号。

### 6.2 確保の解放

`reserved −= (reservation.quantity − reservation.shortage_quantity)`、reservation を RELEASED、`expires_at = NULL`。履歴なし。

### 6.3 欠品の登録（API-16）

前提：注文が PREPARING、決済が AUTHORIZED（それ以外は409 `INVALID_STATE`）。

明細ごとに新しい欠品数 `new_shortage`（0以上、ordered以下、既存の欠品数以上）を受け取る。増えた分 `Δ = new_shortage − 既存の欠品数` について：

- `reserved −= Δ`
- 実際に帳簿から減らす数 `d = min(Δ, on_hand)`。`on_hand −= d`。`d > 0` のときだけ履歴 `EC_SHORTAGE`（delta −d、reference `ORDER_ITEM`）を書く（帳簿在庫と履歴の合計を一致させるため）。
- `order_items.shortage_quantity = new_shortage`、reservation の `shortage_quantity = new_shortage`

その後、全明細で `shortage_quantity = ordered_quantity` なら、または `shortage_policy = CANCEL_ALL` で欠品が1つでもあれば、注文を取り消す（T6）。理由は前者が `SHORTAGE_ALL`、後者が `SHORTAGE_POLICY`。残りの確保は6.2で解放し、決済を RELEASING（新しい操作）にしてコミットした後、RELEASE を呼ぶ。取消にならない場合は、メール `SHORTAGE_CHANGED`（変更後の金額を記載）を送る。

### 6.4 準備完了の出庫（T7）

明細ごとに `consumed = ordered − shortage`：

- API-18の段階1で、各明細について `consumed <= on_hand` を確認する。満たさなければ capture を呼ばずに409 `INSUFFICIENT_STOCK`（`details` に該当明細。画面は「帳簿在庫が足りません。欠品を登録してください」）。
- 段階3（capture成功後）：`reserved −= consumed`。実際に減らす数 `d = min(consumed, on_hand)`、`on_hand −= d`、`d > 0` なら履歴 `EC_PICKUP_OUT`（delta −d）。`d < consumed` の場合（段階1と段階3の間に棚卸で減った場合）はWARNINGログを出す
- `order_items.prepared_quantity = consumed`
- reservation を SETTLED、`consumed_quantity = consumed`

### 6.5 店舗へ戻す（READY後の取消・期限切れ）

`prepared_quantity > 0` の明細だけ、`on_hand += prepared_quantity`、履歴 `EC_CANCEL_RETURN`（取消）または `EC_EXPIRED_RETURN`（期限切れ）。

### 6.6 入荷・棚卸・破損

| 種類 | 入力 | 処理 | エラー |
|---|---|---|---|
| 入荷 RECEIVE | quantity（1〜9,999）、reason（任意） | `on_hand += quantity` | |
| 棚卸 STOCKTAKE | countedQuantity（0〜99,999）、reason（差分ありなら必須） | `delta = counted − on_hand`、`on_hand = counted`、履歴の `counted_quantity = counted` | 差分ありで理由なし → 400 `VALIDATION_ERROR` |
| 破損 DAMAGE | quantity（1以上、on_hand以下）、reason（必須） | `on_hand −= quantity` | on_hand超 → 409 `INSUFFICIENT_STOCK` |

更新後に `on_hand < reserved` なら、レスポンスの `shortageRiskQuantity` に `reserved − on_hand` を入れ、`shortageRiskOrderCount` に影響する注文数（その在庫行の CONFIRMED 確保を持つ RECEIVED・PREPARING の注文数）を入れる。登録自体は拒否しない。

### 6.7 POS売上の取消

当日（`sold_at` を Asia/Tokyo に変換した日付が今日）・自店舗・COMPLETED の売上だけを取り消せる。明細ごとに `on_hand += quantity`、履歴 `POS_VOID`。売上を `VOIDED`、`voided_at`、`voided_by`、`void_reason` を設定する。

## 7. 遅延

### 7.1 店員による遅延登録（API-17）

- 対象：RECEIVED・PREPARING・ACTION_REQUIRED。
- 入力：`reasonCode`（`STAFF_SHORTAGE`・`CONGESTION`・`STOCK_CHECK`・`OTHER`）、`reasonText`（OTHERなら必須で1〜200文字。それ以外は省略可で、省略時はコードの表示名を使う）、`updatedReadyAt`（NULLは確認中。値があるなら `now` より後で、「今日が営業日で閉店前なら今日の閉店時刻、そうでなければ次の営業日の閉店時刻」以前。範囲外は400 `VALIDATION_ERROR`）。
- 処理：`order_delays` を追加（source STAFF）、`is_delayed = true`、`delay_occurred = true`、`updated_ready_at = updatedReadyAt`、メール `DELAYED`、監査 `DELAY_REGISTERED`。

理由コードの表示名：STAFF_SHORTAGE＝人手が不足しているため、CONGESTION＝店舗が混雑しているため、STOCK_CHECK＝在庫を確認しているため、OTHER＝入力した文、AUTO_OVERDUE＝予定時刻を過ぎています（店舗で確認中）。

### 7.2 予定超過の自動遅延

条件：status が RECEIVED・PREPARING・ACTION_REQUIRED、かつ `now > coalesce(updated_ready_at, original_ready_at)`、かつ「確認中の遅延中」（`is_delayed = true AND updated_ready_at IS NULL`）ではない。

処理：`order_delays` を追加（source AUTO、reason_code AUTO_OVERDUE、new_ready_at NULL）、`is_delayed = true`、`delay_occurred = true`、`updated_ready_at = NULL`、メール `DELAYED`、監査 `DELAY_AUTO`。

### 7.3 購入者による取消（API-12、T5）

1. 注文行・決済行をロックし、4章末尾の順で判定する。取消条件（`canCancel`）を満たさなければ422 `CANCEL_NOT_ALLOWED`。
2. トランザクション1：注文を CANCELLED（`cancelled_at`、`cancel_reason_code = BUYER_DELAY`、`version += 1`）。RECEIVED・PREPARINGなら確保を解放（6.2）し、決済を RELEASING（新しい操作）にする。READYなら店舗へ戻す（6.5、`EC_CANCEL_RETURN`）、QRトークンを `revoked_at = now`・`revoked_reason = CANCELLED` にし、決済を REFUNDING（新しい操作）にする。`operation_started_at = now`。メール `CANCELLED`。コミット。
3. トランザクション外：RELEASE または REFUND を呼ぶ。
4. トランザクション2：結果を反映する。失敗・結果不明でも注文は CANCELLED のままとし、決済は FAILED・UNKNOWN として J-03 が照合・再試行する。

## 8. 時間で変わる状態の同期

Freeプランでは常駐の定期処理を使えないため、時間で変わる状態は「読むときに確定させる」。関数 `sync_time_based_state(order, now)` は注文行をロックしたうえで、次を順に行う。

1. 7.2の条件を満たせば自動遅延にする。
2. status が READY で `now > pickup_deadline_at` なら EXPIRED にする（T13）。

呼び出す場所：

| 呼び出し元 | 対象 |
|---|---|
| API-10（注文一覧）・API-11（注文詳細） | 返す注文 |
| API-14（店員の注文一覧） | 自店舗の RECEIVED・PREPARING・ACTION_REQUIRED・READY の注文すべて |
| API-41（店員の注文詳細） | その注文 |
| API-15〜18・API-20・API-35（店員の操作） | 操作する注文（version の確認の後、状態の判定の前に行う。4章末尾） |
| API-19（受け取り照合） | 照合する注文 |
| J-01・J-05 | 全店舗 |

APIの中で行う同期は注文の行ロックだけで行い、ジョブのアドバイザリロックは取らない（ジョブと同時に動いても、行ロックと冪等な処理で結果は同じになる）。

メールはコミット後に送る（10章）。

## 9. 認証・QR

### 9.1 パスワード

- `argon2-cffi` の `PasswordHasher()`（既定パラメータ）でハッシュ化する。
- 長さ12〜128文字。その他の文字種の条件は設けない。

### 9.2 アクセストークン（JWT）

- 署名：HS256、鍵は `JWT_SECRET`（32バイト以上のランダム文字列）。
- クレーム：`iss="pickup-app-backend"`、`aud="pickup-app-bff"`、`sub=ユーザーID`、`role`、`store_id`（店員のみ）、`iat`、`exp=iat+15分`、`jti=UUID`。
- Backendは `Authorization: Bearer <JWT>` から読み、署名・`exp`・`iss`・`aud` を検証する。失敗は401 `UNAUTHENTICATED`、期限切れは401 `TOKEN_EXPIRED`。
- ユーザーが DISABLED なら401。

### 9.3 リフレッシュトークン

- 生値：`secrets.token_urlsafe(32)`。DBには SHA-256 だけを保存する。
- API-03で使うたびに、古いトークンを `revoked_at = now`、`replaced_by_id = 新ID` にし、新しいトークンを発行する（ローテーション）。
- 失効済みのトークンが使われた場合：ローテーションで失効してから30秒以内（`replaced_by_id` があり `revoked_at > now − 30秒`）なら、何も失効させずに401 `UNAUTHENTICATED` を返す（同時に更新した要求への猶予）。それ以外は、そのユーザーの有効なリフレッシュトークンをすべて失効させ、401を返す（盗用の疑い）。
- BFFは同じリフレッシュトークンでの更新を1回にまとめる（02_API詳細 2.4）。
- API-04（ログアウト）で失効させる。

### 9.4 試行回数の制限

`rate_limit_counters` を使う。カウンタの読み書きは業務処理とは別のトランザクション（すぐにコミット）で行い、業務処理のロールバックで消えないようにする。

1. 要求の最初に、キーの行を読む。`window_started_at + 窓 < now` なら期限切れとして扱う（count 0）。`count >= 上限` なら429 `RATE_LIMITED`（`Retry-After` ヘッダーに窓の残り秒数）。
2. 数える対象（下表）が起きたら、行がないか期限切れなら `count = 1`・`window_started_at = now` で作り直し、そうでなければ `count += 1` してコミットする（MySQLの `INSERT ... ON DUPLICATE KEY UPDATE`（SQLAlchemyのMySQL用insert式））。

| 対象 | キー | 数えるもの |
|---|---|---|
| ログイン | `login:{小文字化したemailのSHA-256（16進64文字）}` | 失敗だけ。成功したら行を削除 |
| QR照合 | `pickup_qr:{店員ID}` | すべての照合要求 |
| 手入力照合 | `pickup_manual:{店員ID}` | 失敗だけ |

### 9.5 受け取りQRと手入力コード

- トークン発行：READYになったとき `pickup_tokens` に1行作る（`token_id = uuid4()`、`issued_at = now`）。
- QRの文字列：`PA1.` ＋ base64url（パディングなし）の `payload` ＋ `.` ＋ base64url の署名。
  - `payload = {"o": 注文ID, "t": トークンID, "i": issued_atのUNIX秒}` を `separators=(",",":")`、キー順 `o,t,i` でJSON化したUTF-8
  - 署名 = `HMAC-SHA256(QR_SECRET, "PA1." + base64url(payload))`
  - 同じトークンなら何度表示しても同じ文字列になる。
- 手入力コード（6桁）：`int.from_bytes(HMAC-SHA256(QR_SECRET, "MANUAL." + トークンID)[:4], "big") % 1000000` を6桁ゼロ埋め。注文番号と組み合わせて入力する。
- 照合（API-19）は9.6に従う。
- 再発行（API-37）：購入者が READY・EXPIRED の注文で実行すると、有効なトークンを `revoked_at = now`・`revoked_reason = REISSUED` にし、新しいトークンを発行する。

- QRの表示可否：status が READY または EXPIRED、かつ payments が CAPTURED、かつ有効なトークンがある。
### 9.6 受け取り照合と引き渡しの判定

**照合（API-19）**

1. 試行回数の制限（9.4）：QRは `pickup_qr:{店員ID}` を要求ごとに数える。手入力は `pickup_manual:{店員ID}` を、失敗（下の2・3で INVALID_PICKUP_CODE になった場合）のときだけ数える。
2. トークンの特定：
   - QR：形式と署名を検証する（`hmac.compare_digest`）。失敗、またはトークン行がない、注文IDが一致しない、`revoked_reason = REISSUED` なら422 `INVALID_PICKUP_CODE`。
   - 手入力：注文番号の注文が自店舗でない、または存在しない場合は422 `INVALID_PICKUP_CODE`（他店舗の注文の存在を明かさない）。その注文の最新のトークン（`issued_at` が最も新しいもの）の手入力コードと一致しなければ422 `INVALID_PICKUP_CODE`。トークンがない（まだ準備完了していない）場合も同じ。
3. QRの注文が他店舗なら、200で `canHandOver=false`、`reasonCode=OTHER_STORE`、`orderNumber` だけを返す（明細などは返さない）。
4. 注文行をロックして8章の同期を行う。
5. 次の順に判定し、該当すれば200で `canHandOver=false` と理由を返す：トークンの `used_at` がある、または status が PICKED_UP → `ALREADY_PICKED_UP`。CANCELLED → `CANCELLED`。EXPIRED_RETURNED → `RETURNED_TO_STOCK`。READY・EXPIRED 以外 → `NOT_READY`。決済が CAPTURED でない → `PAYMENT_NOT_CAPTURED`。
6. 引き渡し可能なら `canHandOver=true`、`pickupVerificationId = トークンID`、明細、`version` を返す。

**引き渡し（API-20）**

注文行をロックし、次の順に判定する：①`version` 不一致 → 409 `CONFLICTING_UPDATE` ①の後に8章の同期を行い（自己同期でversionが増えても①を再実行しない）、②status が READY・EXPIRED でない、または決済が CAPTURED でない → 409 `INVALID_STATE` ③`pickupVerificationId` が注文の最新のトークンIDでない、またはそのトークンが失効・使用済み → 422 `INVALID_PICKUP_CODE`。すべて満たせばT12。

## 10. メール

### 10.1 送信方式

- 業務処理のトランザクション内で `notifications` を PENDING で登録し、コミット後に FastAPI の `BackgroundTasks` で送信処理を呼ぶ。取りこぼしは J-04 が送る。
- 送信処理は、対象の行を `SELECT … FOR UPDATE SKIP LOCKED` で取り、`status = PENDING AND next_attempt_at <= now` のものだけを送る（BackgroundTasks と J-04 が同じメールを二重に送らないため）。
- 環境変数 `MAIL_MODE`：
  - `simulate`（既定）：実際には送らず、status を SIMULATED、`sent_at = now` にする。内容は開発用画面（DEV-01）で確認する。
  - `smtp`：`SMTP_HOST`・`SMTP_PORT`・`SMTP_USERNAME`・`SMTP_PASSWORD`・`MAIL_FROM` で STARTTLS 送信する。成功は SENT。
- 試行のたびに `attempt_count += 1`。失敗時は `last_error_code` に例外の種類名、`next_attempt_at = now + 2^(attempt_count−1) 分`。`attempt_count >= 5`（最初の送信を含めて5回試みた）で FAILED。
- 本文はプレーンテキスト。注文詳細のURLは `FRONTEND_BASE_URL + "/orders/" + 注文ID`。

## 12. 定期ジョブ

### 12.1 実行方法

- Backendの関数 `run_jobs(job_codes)` として実装する。各ジョブは、ジョブ専用に取得したDB接続で `GET_LOCK(CONCAT('pickup:', DATABASE(), ':', ジョブコード), 0)`（戻り値1だけ取得成功、0は取得できず、NULLはDBエラー） を取れたときだけ実行し、取れなければ `SKIPPED_LOCKED` を記録する。実行後は `finally` で 同じ接続で `RELEASE_LOCK` を呼び、その接続を閉じる（接続プールに戻したままロックが残らないようにする）。業務の更新は別のセッションで、対象1件ごとにコミットする。実行結果は `job_runs` に記録する。
- 呼び出し方は3つ：
  1. API-38 `POST /internal/jobs/run`（GitHub Actions の定期実行から呼ぶ。05_インフラ・設定 5章）
  2. 管理コマンド `python -m app.cli jobs run [J-01 ...]`
  3. 8章のように、APIの処理の中で対象の注文だけ同期する（アドバイザリロックは取らない）
- 各ジョブは1回あたり最大100件を処理し、残りは次回に回す。何度実行しても結果が変わらないようにする。

### 12.2 ジョブ一覧

| ID | 名前 | GitHub Actionsでの実行間隔 | 処理 |
|---|---|---|---|
| J-01 | 予定超過の遅延 | 10分ごと | 全店舗の対象注文に7.2を適用 |
| J-02 | 期限切れの見積もり・仮確保 | 10分ごと | ①`status=HELD AND expires_at <= now` の見積もりを EXPIRED。②`status=PENDING_PAYMENT AND hold_expires_at <= now` の注文：12.4の手順 |
| J-03 | 決済の照合 | 10分ごと | 12.5の表の対象を処理する |

### 12.4 J-02：期限切れの支払確認中の注文

1. PaymentIntent を取得する（IDがなければ search。注文の作成から5分未満なら次回に回す）。
2. 見つからない → 決済を FAILED（`failure_code = NOT_CREATED`）にして T3。
3. `requires_capture` → 決済を AUTHORIZED（`authorized_confirmed = true`）として記録する（T2は行わない）。続けて4へ。
4. `canceled`・`requires_payment_method` 以外（`requires_capture`・`requires_action` 等）→ 期限後に受付を成立させないため、決済を RELEASING（新しい操作）にしてコミットし、cancel を呼んで5.3で反映し、T3。
5. `canceled`・`requires_payment_method` → 5.3で反映して T3。

### 12.5 J-03：決済の照合の対象と処理

「古い」は `operation_started_at <= now − 5分`。どの行も `operation_attempt` が5に達したら再実行せず、WARNINGログを出す（管理コマンドで対応）。

| 対象の決済 | 処理 |
|---|---|
| AUTHORIZING・REQUIRES_ACTION・UNKNOWN(AUTHORIZE) で古いもの | PaymentIntent を取得（IDがなければ search）して5.3で反映。見つからなければ何もしない（注文の期限切れ後に J-02 が処理する） |
| CAPTURING・UNKNOWN(CAPTURE) で古いもの | PaymentIntent を取得して5.3で反映。まだ `requires_capture` なら同じキーで capture を再送する |
| FAILED(CAPTURE) で注文が ACTION_REQUIRED | PaymentIntent を取得し、`succeeded` なら5.3で反映（T9）。`requires_capture` なら `operation_attempt += 1` で capture を再実行する。それ以外（与信の失効など）は何もしない（管理コマンドで取消） |
| RELEASING・UNKNOWN(RELEASE) で古いもの | PaymentIntent を取得して5.3で反映。まだ `requires_capture` なら同じキーで cancel を再送する |
| FAILED(RELEASE) で `failure_code != CANCELED_BEFORE_AUTHORIZATION` | PaymentIntent を取得し、`canceled` なら5.3で反映して終える。`requires_capture` なら `operation_attempt += 1` で cancel を再実行する |
| REFUNDING・UNKNOWN(REFUND) で古いもの | `provider_refund_id` があれば Refund を取得して反映。なければ `Refund.list(payment_intent=…)` で探し、あればIDを保存して反映、なければ同じキーで Refund.create を再送する |
| FAILED(REFUND) | `operation_attempt += 1` で Refund.create を再実行する |

## 13. 冪等性（Idempotency-Key）

対象API（02_API詳細で「冪等キー：必須」としたもの）は、ヘッダー `Idempotency-Key`（UUID）が必須。ないか形式が違えば400 `VALIDATION_ERROR`。

- `endpoint` は「メソッド＋実際のパス」（例：`POST /api/v1/orders/1f…/cancel`）。
- `request_hash` はリクエスト本文の正規化JSON（キーを辞書順、空白なし）のSHA-256。本文がなければ空文字列のSHA-256。

1. 独立したトランザクションのSAVEPOINT内で `(user_id, endpoint, key)` の行のINSERTを試す。MySQLエラー1062だけ既存行として扱い、他のエラーは伝播する。新規行を作る（`response_status = NULL`、`locked_until = now + 2分`、`expires_at = now + 24時間`）。挿入できたら、そのまま処理へ進む。
2. 挿入できなかった（既存の行がある）場合、その行を `SELECT ... FOR UPDATE` で読んで判定・更新する：
   - `request_hash` が違う → 422 `IDEMPOTENCY_KEY_REUSED`。
   - `response_status` がある → 保存したレスポンス（ステータスと本文）をそのまま返す。
   - `response_status` がNULLで `locked_until > now` → 409 `IDEMPOTENCY_IN_PROGRESS`。
   - `response_status` がNULLで `locked_until <= now`（前の処理が異常終了した）→ `locked_until = now + 2分` に更新して処理へ進む。
3. 処理が終わったら、レスポンスのステータスと本文を保存する。500系で終わった場合は行を削除する（再試行できるようにするため）。ただしAPI-09の段階1がコミットされた後は5xxで終わらせない（3.5）。

Frontendは「操作1回につき1つのキー」を生成し、通信エラーで再送するときは同じキーを使う。画面で入力内容を変えて再操作するときは新しいキーを使う。
