# ステップ6 実装結果

確認日：2026年11月3日（日本時間）。見積もり・注文受付・決済連携・メールのコードとローカル検証を実施しました。実Stripeのテストキーはまだ仮設定のため、実Stripeとのカード入力・3Dセキュア接続試験は未実施です。既存の未コミット変更を維持し、commit・push、Azureへの更新・初期化は行っていません。

## 実装内容

### 見積もりと注文

- API-08 `POST /api/v1/orders/estimate`：合計10点、SKU・店舗・受付・在庫の検証、作業時間と予定の計算、見積もり10分保持。同一利用者の前回見積もりを先行作業から除外し、受付不可なら前回の見積もりを残して理由を返します。
- 先行作業は当日の見積もり時刻順。注文への変更後も元の位置を使い、後からの見積もりや経過時間だけで当初予定を遅らせません。受付締切ちょうど、開店前、分単位への切り上げ、60分上限、閉店15分前を計算に反映しました。
- API-09 `POST /api/v1/orders`：見積もり・明細ハッシュ・受取条件への同意・在庫・金額・予定を再検証。注文、スナップショット明細、在庫仮確保、決済処理中、監査を保存します。
- 店舗→見積もり→在庫ID昇順のロック、既存採番行のロックを使用。Order・PaymentのUPDATEにもversion条件を追加。EC確保とPOSは同じ在庫行で競合を防止します。
- 決済サービスはDBのトランザクションを閉じてから呼びます。段階1をコミットした後の想定外エラーは202と注文IDを返し、別注文としての再送を防ぎます。
- 冪等キーの行に注文IDを段階1と同時保存。処理が中断してキーのロックが切れた場合も、新しい注文・再与信を作らず復元します。MySQLのCOMMITだけ成功して応答が失われたケースも検証しました。

### 決済

- `PaymentGateway`、`StripePaymentGateway`、テスト専用の `FakePaymentGateway` を追加。与信・取得・検索・確定・取消・返金・返金取得／一覧のインターフェースを用意しました。
- Stripe SDK v16の `StripeClient.v1` を使用。JPY、手動確定、ConfirmationToken、10秒タイムアウト、操作別のStripe冪等キーを指定します。失敗が確定した例外と結果不明の例外を分け、アプリのログへStripe例外の本文をコピーしません。
- 与信成功はRECEIVED／AUTHORIZED、追加認証はPENDING_PAYMENT／REQUIRES_ACTION、拒否はNOT_ACCEPTED／FAILEDと在庫解放、応答不明はPENDING_PAYMENT／UNKNOWN。
- API-36 `POST /api/v1/orders/{orderId}/payment/refresh`：購入者本人の注文だけ取得し、PaymentIntent IDが保存済みの支払確認中注文だけStripeへ照会します。
- API-13：生の本文で署名を検証。イベント行の独立した確保・重複防止、トランザクション外でのStripe再取得、署名済み本文の状態値を使わない反映、ERRORからの再処理を実装しました。金額・通貨・テストモード・注文のmetadata・既存PaymentIntent IDも照合します。
- 与信の反映はWebhook・注文応答・追加認証後の確認で共通化。古いイベントで状態を戻さず、受付メールや在庫解放を重複させません。確定／解放／返金の店舗操作・ジョブによる後続の状態遷移は対応する後続ステップで追加します。

### 注文画面とメール

- C-06〜C-10：注文・受取条件の確認、欠品方針、期限切れ時の再見積もりと変更案内、Stripe Payment Element、追加認証後の確認、受付結果、注文一覧・詳細。
- 通信結果が不明な再試行は、同じConfirmationToken・本文・Idempotency-Keyを使います。Stripe側のトークン作成中から連打を抑止。追加認証を閉じてもAPI-36を呼び、受付結果へ進みます。
- 受付結果は支払確認中だけ5秒ごと・最大2分照会。RECEIVEDでカートを空にします。購入者以外・未ログインの注文手続きは画面とAPIで制限します。
- API-10・11：本人の注文のみ取得。他人の注文は404。読む際の自動遅延・期限切れ同期と通知登録も追加。QR・再発行・取消の画面操作はステップ8まで有効にしません。
- メールは業務トランザクション内でPENDING登録し、コミット後のBackgroundTasksで処理。simulateではSIMULATEDへ更新。SMTPはSTARTTLSで送信し、失敗時は1・2・4・8分で再試行、5回でFAILED。SKIP LOCKEDで同時送信を抑制します。
- API-39／DEV-01：本人宛て、または担当店舗のメールだけ表示。Backendの開発フラグfalseは404、Frontendも公開用の開発フラグfalseなら404にします。
- BFFの許可リストと、OpenAPIから生成するFrontend型を更新しました。カード番号・CVCはアプリへ送らず、受取QRなどの後続機能は追加していません。

## 実Stripe接続試験に残っていること

`backend/.env` の `STRIPE_SECRET_KEY`・`STRIPE_WEBHOOK_SECRET`、`frontend/.env.local` の `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` は仮設定です。同じStripeテストアカウントの実際のテストキーをGit対象外ファイルに設定し、カードのみを有効にして、成功・拒否・3Dセキュア（E2E-02・03）と実Webhookを確認する必要があります。実際のSMTP送信も未実施で、simulateとテスト送信関数で検証しています。

通常起動ではStripe用処理を使用します。リクエスト・環境変数からFakeへ切り替える機能は設けていません。実Stripeキーがない状態で、決済を成功したように表示することはありません。

実装の参照：[Stripeのサーバー側確定フロー](https://docs.stripe.com/payments/finalize-payments-on-the-server?platform=web&type=payment)、[Stripe Python SDK](https://github.com/stripe/stripe-python)。実装時にはインストール済みSDK v16とStripe.jsの型も照合しました。
